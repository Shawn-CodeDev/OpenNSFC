# 阶段 0 — 环境与定位

> **目标**：确认环境就绪、确定研究属性与项目定位、建立页数预算。
> **前置**：无（流程起点）
> **产出**：`work/state.json` 的 `researchAttribute` / `scope` / `pageBudget`
> **可跳过**：**不可跳过**

---

## 步骤

### 1. 环境自检

```bash
node bin/doctor.mjs
```

- 有 `fail` 项 → 运行 `node bin/setup.mjs` 自动配置（会自动挑选 CTAN 镜像并安装 TeX Live）
- 仅 `warn`（如 TeX Live 缺失）→ 可继续，但需告知用户阶段 9 只能出 Markdown/HTML，无 PDF

**不要假设环境可用，必须实际运行。**

### 2. 读取申请人覆盖文件（若存在）

检查 `overrides/` 目录：

| 文件 | 用途 |
|---|---|
| `applicant.yaml` | 申请人姓名、职称、单位、申请代码、执行期限 |
| `foundation.md` | 研究基础、前期成果、预研数据 |
| `conditions.md` | 工作条件、算力资源、在研项目 |

存在则读入并在后续阶段直接使用，避免重复询问。不存在则逐项向用户收集。

### 3. 收集项目基本定位

向用户收集（缺失则逐项询问，**不要代填**）：

1. **研究主题**：项目研究什么？
2. **学科领域与申请代码**：如 F0601（人工智能）
3. **申报类型与级别**：国自然青基（C类）/ 面上 / 省基金

### 申报类型决定篇幅配比（**必须先定，后续所有阶段都受影响**）

两种类型的实测配比差异极大（依据两份已获批申请书的真实统计，
见 `docs/获批本解剖.md` 第 11 节）：

| 章节 | 青年基金 | 面上项目 | 含义 |
|---|---:|---:|---|
| 立项背景与意义 | 11% | **6%** | 面上更不靠"重要性"取胜 |
| **国内外研究现状** | 15% | **31%** | **面上要把现状写厚近一倍** |
| 研究目标 | 4% | 1% | 面上更短 |
| 研究内容 | 5% | 4% | 相当 |
| 关键科学问题 | 4% | 4% | 相当 |
| 主要研究方案 | **41%** | **33%** | 两者最重 |
| **可行性分析** | 8% | **12%** | 面上证据更多 |
| 特色与创新 | 6% | 5% | 相当 |
| 年度计划 + 预期成果 | 4% | 6% | 面上常独立出"预期研究成果" |
| 正文字数 | ~15,000 | ~29,000 | **面上 ≈ 1.9×** |
| 内文引用 | ~30 | ~79 | 面上 ≈ 2.6× |

**面上项目因此有两条额外硬要求**（在阶段 6/7/8 中执行）：

1. **研究内容必须有一条「统一抽象」串起来**。面上范围大，若四条研究内容读起来是
   "四个不相干的课题"，是面上本最常见的被否原因。实测样本用一个概念把四条锁成整体
   （如案例 B 用「关系」：构型关系 / 拓扑关系 / 依附关系 / 时序关系）。
   → **阶段 7 必须显式产出并核对这条抽象。**
2. **可行性分析需要三类可核验的硬证据**：平台与产业合作（单位名）、
   数据与知识产权（专利公开号、软著号、数据集规模）、**实机测试的对比数字**。
   → **阶段 8 必须逐项追问**，缺则明确留空，不得编造。

> **2026 版篇幅约束**：官方改为"不超过 30 页（含图表）"。实测面上样本为 41 页、
> 青年样本为 22 页——**面上项目迁移到 2026 版需压缩约 27%**，
> 压缩顺序建议：研究意义 > 现状的次要分支 > 创新点重复表述，
> **不压研究方案与可行性**。
4. **项目执行期限**：如 2027-01 至 2029-12
5. **最终交付物**：完整申请书 / 仅立项依据 / 仅调研报告

写入 `state.json.scope`。

### 4. 确定科学问题属性（**最关键的一步**）

按 §Runbook 6.2 的判定法确定，并**让用户确认**。

判定辅助：

| 判定法 | 倾向 |
|---|---|
| 问题源于明确的外部需求或工程瓶颈 | 目标导向类 |
| 答案形态为"某机制 / 某界限 / 某条件 / 某构造" | 自由探索类 |
| 答案形态为"我们实现了某系统，效果更好" | 该问题更可能是 technology，需重新提炼 |

### 5. 科学问题形态预检（提前拦截最常见失败）

让用户用一句话回答："**这个项目要回答什么问题？**"

| 用户给出的形态 | 判定 | 处理 |
|---|---|---|
| "如何在不依赖 A、B 的条件下实现 X" | ❌ 技术目标 | 追问：X 失效的**机理**是什么？ |
| "如何把某指标提升到某水平" | ❌ 指标目标 | 追问：为什么现在达不到？设计缺陷还是数据不足？ |
| "某现象是否源于某机理？" | ✅ 科学问题 | 继续 |
| "在某约束下是否存在某类方法的界限？" | ✅ | 继续 |
| "是否存在某结构使原问题可解？" | ✅ | 继续 |

**预检未通过时不要继续检索**——先把问题形态纠正过来。官方评审指导明确要求关键科学问题"是 science，不是 technology"。

### 6. 建立页数预算

正文原则上**不超过 30 页**（含图表）。默认分配：

```json
"pageBudget": { "total": 30, "part1": 9, "part2": 17, "part3": 3, "references": 1 }
```

分配原则：**（二）研究内容**是官方唯一要求"按自身逻辑自主撰写"的部分，应占正文 50% 以上。

### 7. 记录 AI 使用情况

询问用户本项目是否使用 AI 辅助撰写、用于哪些部分，写入 `state.json.aiDisclosure`。**必须如实**——官方在（四）第 5 项明确要求披露。

## 完成判据

### 硬判据

- **H1**：`bin/doctor.mjs` 无 `fail` 项
- **H2**：`researchAttribute.type` 已确定且为用户**明确确认**（`confirmed: true`），非 agent 代选
- **H3**：`scope` 五项齐全（主题、领域、级别、期限、交付物）
- **H4**：科学问题形态预检通过（或已记录为待纠正项）
- **H5**：`pageBudget` 已建立

### 软判据

- **S1**：`researchAttribute.rationaleDraft` 已收集（系统填报需要）
- **S2**：`aiDisclosure` 已如实填写
- **S3**：已向用户说明"本技能包不能替你产出科学洞察"这一边界

### 评级

- **优**：H1–H5 + S1–S3 全部满足，且科学问题已是可证伪形态
- **良**：H1–H5 + S1–S2
- **中**：H1–H5 满足但科学问题形态待纠正
- **差**：任一 H 不满足
