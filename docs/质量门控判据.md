# 质量门控与验收判据

> 本文件由 `write-proposal` 编排器在执行门控检查时逐条使用。
> 目的：把"写了文件就算完成"改为"通过判据才算完成"，并对齐基金委官方的综合评价等级。

## 一、门控机制

### 执行规则

1. 任一 section 完成后，编排器**必须**执行该 section 的判据检查
2. 判据分两类：
   - **硬判据（H）**：任一不满足即 `gate = fail`，不得推进
   - **软判据（S）**：用于确定评级 `grade`，不单独导致 fail
3. `gate = fail` 时**禁止推进阶段**，必须列出未达标项并要求迭代
4. `gate = pass` 且 `grade` 为 `优` 或 `良` 时方可推进
5. 同一 section 连续 **3 轮**迭代仍为 `fail`：提示用户**研究设计本身可能需要调整**，而非继续改文字

### 评级标准（对齐基金委官方定义）

| 等级 | 官方定义 |
|---|---|
| **优** | 创新性强，有重要科学研究价值或应用前景，总体研究方案合理可行 |
| **良** | 立意新颖，有较重要的科学研究价值或应用前景，总体研究方案较好 |
| **中** | 有一定的科学研究价值或应用前景，总体研究方案尚可，某些关键方面存在不足 |
| **差** | 某些关键方面有明显缺陷 |

### 评级映射

- **优**：全部硬判据通过，软判据满足 ≥90%
- **良**：全部硬判据通过，软判据满足 ≥70%
- **中**：全部硬判据通过，软判据满足 <70%（有关键方面不足）
- **差**：存在硬判据未通过（有明显缺陷）

## 二、专项门控：可证伪性检查（全篇核心）

**这是本项目最容易被评审击穿的地方，单独设为一组门控。**

对 S1 与 S6 提出的每一个科学问题，逐项检查：

| 检查项 | 通过标准 |
|---|---|
| **H-1 可证伪** | 能明确指出"什么实验结果会否定该假说"。写不出即 fail |
| **H-2 是 science** | 问题的答案形态是"某机制/某界限/某条件"，不是"我们实现了某系统" |
| **H-3 非技术目标** | 不出现"如何在不依赖 A、不依赖 B、不依赖 C 的条件下……"这类约束排比 |
| **H-4 非指标目标** | 不出现"如何将某指标提升到某水平"作为科学问题 |
| **H-5 数量收敛** | 关键科学问题 1-2 个（不是 3-5 个） |
| **H-6 与假说一致** | S6 的关键科学问题与 S1 的科学假说严格对应，无另起炉灶 |
| **S-1 限定条件** | 假说写明了成立的条件或范围 |
| **S-2 可观测推论** | 假说给出了"若成立则可观察到什么" |
| **S-3 判据可测** | 可观测推论是技术上可测量的 |

## 三、逐 section 门控判据

### 5.1 哪些判据已有脚本可自动查（**先跑脚本，再做人工判断**）

上面这份清单里，**能自动查的不要靠人眼**——人眼通读的漏检率在下面几类上极高。
出稿阶段先按顺序跑完这四个脚本，全部通过后再做人工清单：

| 脚本 | 覆盖的判据 | 退出码约定 |
|---|---|---|
| `bin/check-template.mjs --track <类型>` | 提纲标题逐字一致、四部分顺序、30 页上限 | 0 通过 / 1 有未通过项 |
| `bin/cli.mjs validate --strict` | 参考文献双向对应、编号连续、挂空文献、无引用文档 | 0 通过 / **2 阻断** |
| `bin/check-consistency.mjs --strict` | 术语漂移、图表编号连续与引用、错别字、**自我宣称大词**、占位符残留 | 0 通过 / 1 有问题 |
| `bin/pdf-probe.mjs --expect-figure` | 图是否真的嵌入、正文是否为空、页数 | 0 通过 / 1 失败 |

**仍必须人工判断的**（脚本查不了）：

- 科学问题是否可证伪、否定条件是否真的能推翻假说
- 结构性不足是否挖到假设层面（而不是指标层）
- 技术路线图箭头是否有语义
- 消融是否对准声称的创新组件
- 预研发现是否具体（"已开展初步工作"不算）
- 篇幅配比是否与申报类型相符

> **一个实测教训**：一份**已获批**的申请书里存在「半监督/弱监督」混用、正文引「图3」
> 而图注写「图 1」、「微妙级」错字三处硬伤。这类问题**模板校验、引用校验、编译全都不报**，
> 人工通读也漏了——只有 `check-consistency.mjs` 能发现。所以不要因为"读了两遍"就跳过脚本。

## 六、门控失败的处理流程

```
门控检查
  ├─ pass + 优/良  → 推进阶段，写日志
  ├─ pass + 中     → 建议迭代至良以上；若用户接受可推进，但记录风险
  └─ fail          → 列出未达标项 → 针对未达标项迭代 → 重新门控
                       └─ 连续 3 轮 fail → 提示用户：研究设计本身可能需要调整
```

**不得为了推进而放行。** 若用户明确要求跳过门控，应记录该决定并在日志中标注风险项。

## 七、常见"假通过"识别

以下情况表面上满足判据，实际是伪装，检查时需特别警惕：

| 伪装形式 | 识别方法 |
|---|---|
| 科学问题写得像假说，但没有否定条件 | 追问"什么结果会推翻它"，答不出即为技术目标 |
| 不足写了"结构性缺陷"四个字，但内容仍是指标 | 看是否给出了"现有方法的假设是什么、该假设何时不成立" |
| 技术路线图有框有箭头，但箭头无语义 | 追问每个箭头的输入输出，说不出即为装饰 |
| 消融列了，但消融的是无关模块 | 对照 S7 声称的创新组件清单，逐一核对 |
